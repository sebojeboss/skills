# Stack and policy

## When to read

Use when a policy governs the answer, sources conflict, knowledge changed, or another store/market is added. Skip a stack inventory for a straightforward reply with adequate supplied facts.

## How to do the work

Find the helpdesk, order authority, return portal, knowledge store and actual fulfillment owner. Record which system can read or change each fact. A payment record is not a dispatch record. Keep existing tools when they cover the job.

For each applicable policy, record the owner, revision/effective interval, store, product class, market and governing date. A return window may start at purchase, delivery or request; choose the written rule, not the date most conveniently available. Separate ordinary returns from faulty/wrong goods and from discretionary goodwill. Do not resolve conflicting policy text by averaging it. Give the merchant the exact conflict and the affected decision, while continuing any unaffected drafting.

Knowledge maintenance has four observable steps: source edited, content ingested, content enabled, and a representative answer corrected. Inspect the imported material, not just a green sync indicator. Single-page imports can omit linked policies or embedded material. A replacement import may discard prior generated content. If stale content cannot immediately refresh, disable the affected answer where supported and route that intent to review. This trades automation coverage for correct answers; it need not disable unrelated intents.

## Worked decisions

Illustrative: an order was bought outside a return window but delivered inside it. A delivery-based policy makes it premature to deny the return based on purchase date. If another active flow uses purchase date, repair both the flow and knowledge source, then test the boundary on each side. Do not infer that every historical rejection was wrong without the relevant tickets.

## Apply the policy to the case

Use independently established facts and the policy version that governed this buyer/product/market. Compare the written conditions with the supplied case; list matched, failed and unresolved conditions separately. Check the starting date and timezone for a window, both boundaries for a bounded amount, and the currency/units for any cap. A maximum alone does not exclude a negative or mis-scaled value.

Keep eligibility separate from authority: a return may qualify while the current operator lacks authority for the amount or remedy. Missing facts or an empty rule set do not authorize action. If one condition clearly fails while another is unknown, retain both reasons rather than flattening the case into a confident overall verdict. Resolve conflicting policy text with the responsible merchant instead of inventing a rule.

## Deliverable and checks

Deliver the applicable policy/version, unresolved conflict, source freshness and the proposed answer/action. Use [triage](ticket-triage-and-drafts.md) for the reply and [remedy authority](returns-and-remedy-authority.md) for exceptions. A matching condition cannot substitute for an omitted rule or a stale policy.
